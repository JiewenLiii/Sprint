# CIVC 四阀门 AI 辅助开发自评审计报告
本报告基于 **CIVC 四阀门安全管控框架（约束 Constraint / 告知 Inform / 验证 Verify / 纠正 Correct）**，针对本次C++地牢探险控制台游戏大作业的全流程AI辅助开发过程，开展全面自评审计。排查AI辅助开发全流程的合规性、安全性、可控性短板，输出可落地整改方案与标准化执行流程，构建安全、规范、高效、可审计的AI辅助软件开发体系。

- **审计项目名称**：地牢探险模块化C++游戏开发
- **审计框架**：CIVC 四阀门AI管控模型
- **审计日期**：2026年4月26日
- **项目核心交付物**：
  1. 遵循Anthropic渐进式披露范式的`AGENTS.md`项目全局开发规范文档
  2. 4组完整AI Prompt演化迭代实验
  3. doctest框架单元测试用例（伤害/战斗/实体/日志四大核心模块）
  4. Git分支管理+CI自动化编译+PR评审合并流程

---

## 一、约束（Constraint）
### 1.1 当前实施现状
本次开发前期未建立明确的AI操作边界与权限管控体系，AI可无差别访问项目`src`目录下全部代码文件，包含`core`核心战斗逻辑、`entities`实体基类、`world`地图底层、`ui`渲染模块等全部核心源码；
未设置文件读写权限隔离、沙盒测试环境、白名单准入规则，AI生成代码可直接修改、覆盖原有项目代码，无前置拦截校验机制；
后续已通过`AGENTS.md`补充模块依赖约束、禁止操作清单，明确了模块解耦、禁止篡改核心逻辑等红线规则。

### 1.2 现存薄弱问题审计
1. 无核心文件只读保护，AI存在误修改、篡改底层战斗公式、地图视野规则、实体基类架构的风险，极易导致核心玩法失效、项目编译崩溃
2. 未划分AI可编辑/仅可读文件范围，AI可能破坏项目原有分层架构、修改统一命名规范，引发模块循环依赖
3. 无前置沙盒校验，AI错误代码可直接侵入主开发分支，污染稳定代码版本
4. 单次AI请求无强制约束前置声明，AI输出自由度过高，容易生成不符合项目规范的冗余、无效代码

### 1.3 系统性改进优化方案
1. **建立固定文件权限白名单**
   - AI开放**可修改目录**：仅`src/test`单元测试目录、`ui`界面美化辅助代码
   - 核心目录`core/entities/world/input/world`全程锁定只读，禁止AI做任何改动
2. **搭建本地沙盒验证机制**
   AI生成的所有代码，优先在独立沙盒副本中编译运行验证，确认功能合规、无破坏性问题后，再同步至主项目仓库
3. **Prompt全局强制约束前缀**
   所有AI提问固定附加前置约束：`严格遵循AGENTS.md开发规范，禁止修改核心业务底层代码、禁止硬编码魔法数字、禁止破坏模块架构，仅允许输出测试与辅助优化代码`
4. **Git分支权限隔离**
   所有AI相关开发统一在`feature/ai-test-civc`分支完成，校验无误后经PR评审合入主`develop`分支

### 1.4 标准化落地执行流程
1. 开发前：配置核心文件本地只读属性，划定AI操作范围
2. 提问时：附加全局强制约束声明，从源头限制AI行为
3. 输出后：人工快速校验修改路径，违规输出直接作废
4. 合并前：沙盒环境编译、功能全校验，无问题再提交PR

## 二、告知（Inform）
### 2.1 当前实施现状
已向AI完整交付项目整体需求、玩法规则、基础架构；同步提供定稿版`AGENTS.md`全局规范文档、全部源码上下文；
AI可基础理解项目分层架构、模块划分、基础开发规则，能够生成匹配项目风格的基础代码与单元测试；
已完成4轮Prompt迭代优化，补充项目专属细节、场景要求、格式约束，大幅提升AI输出精准度。

### 2.2 现存薄弱问题审计
1. 初期上下文信息颗粒度不足，缺少模块详细职责、函数入参出参、常量定义、业务流程图等深度说明，AI早期输出存在代码不兼容、逻辑偏差问题
2. `AGENTS.md`未设置版本号与迭代变更记录，项目代码更新后，AI无法同步感知最新改动，容易生成过时、已淘汰的冗余代码
3. 初期基础Prompt过于笼统，未明确角色扮演、测试场景、边界覆盖要求，导致AI产出质量参差不齐

### 2.3 系统性改进优化方案
1. **迭代完善AGENTS.md深度内容**
   补充各模块核心函数说明、全局常量定义、数值规则、业务流程逻辑，完善项目全量上下文，保障AI信息完全对称
2. **建立文档版本迭代管理**
   文档头部标注版本号（如v1.0、v1.1），新增版本变更日志，记录每次项目调整内容与原因，确保AI始终获取最新版本规范
3. **沉淀项目专属高质量通用Prompt模板**
   固化角色扮演、任务要求、强制场景、格式约束、示例参考的标准化改进Prompt，大幅降低AI理解偏差

### 2.4 标准化落地执行流程
1. 文档更新：每次项目迭代同步更新AGENTS.md与版本日志
2. 信息同步：每次发起AI请求前，同步引用最新版AGENTS.md作为全局依据
3. 精准提问：复用沉淀后的标准化改进Prompt，减少无效沟通
4. 偏差修正：AI输出存在理解偏差时，补充细节信息重新引导输出

## 三、验证（Verify）
### 3.1 当前实施现状
项目已完整接入`doctest`单元测试框架，完成4组核心模块单元测试开发与整合；
已配置GitHub Actions CI自动化流水线，代码推送/PR提交时，自动执行全项目编译、批量单元测试运行；
目前校验以人工功能测试+自动化编译测试为主，可基础验证代码可运行性与核心功能正确性；
本次AI生成的全部单元测试代码，均完成多场景功能校验，全部测试用例运行通过。

### 3.2 现存薄弱问题审计
1. 自动化校验维度不足，未接入代码覆盖率统计，无法量化测试完整度
2. 人工测试仅覆盖主流正常场景，对边界极值、异常输入、临界逻辑场景覆盖不足，隐藏BUG难以被发现
3. 未设置明确准入校验门槛，低覆盖率、存在隐患的代码仍可发起合并
4. 缺少AI专属输出专项校验标准，无法针对性排查AI生成代码的潜在逻辑漏洞

### 3.3 系统性改进优化方案
1. **扩充全覆盖单元测试用例**
   新增边界值、异常值、极限场景专项测试，确保每个核心函数均覆盖正常场景、边界场景、异常场景三类用例
2. **CI流水线新增覆盖率校验**
   在GitHub Actions中接入`gcov`覆盖率统计工具，设置**≥80%测试覆盖率准入门槛**，不达标则拦截合并
3. **建立四级分层验证机制**
   新增语法校验→编译校验→自动化测试→人工全场景验收的四级校验流程
4. **固化AI代码专项验收清单**
   校验规范匹配度、逻辑兼容性、架构合规性、功能完整性四大维度

### 3.4 标准化落地执行流程
1. 初验：AI生成代码，先做语法、命名、规范匹配人工初筛
2. 编译：本地完整编译项目，确保无语法报错、无编译警告
3. 自动化校验：本地运行全部doctest测试用例，同步触发CI自动化检查
4. 覆盖率核验：查看测试覆盖率报告，确认达标
5. 人工全量验收：实际运行游戏，遍历全部核心玩法流程
6. 准入合并：全部校验通过，才可允许合入主开发分支

## 四、纠正（Correct）
### 4.1 当前实施现状
当前错误纠正依赖人工手动修改、AI重新生成；依托Git版本控制基础能力，可执行版本回滚操作；
开发过程中已稳定维护Git分支提交记录，每次合规变更均留存完整提交日志，可追溯开发历史；
暂无自动化一键回滚、错误快速复盘、问题根源定位的标准化机制。

### 4.2 现存薄弱问题审计
1. 无分级错误处置方案，遇到不同等级代码错误，处置流程混乱、效率低下
2. 未提前备份项目稳定基线版本，严重错误发生时，恢复难度大、开发进度受影响
3. 无自动化一键回滚工具，手动Git回滚门槛高、操作繁琐，有误操作风险
4. 错误发生后缺少复盘闭环，同类AI生成问题容易重复出现

### 4.3 系统性改进优化方案
1. **建立三级分级错误纠正体系**
   - 轻微错误（格式、注释、命名）：局部修正+AI定向微调
   - 中等错误（单功能异常、测试不通过）：分支回滚+精准反馈重生成
   - 严重崩溃错误（编译失败、核心损坏）：基线备份一键恢复+全面复盘
2. **稳定版本基线定期备份**
   每次验证完成、功能稳定后，创建Git标签标记稳定基线版本，随时可快速回退
3. **编写一键自动化回滚脚本**
   封装Git常用回滚、重置命令，实现一键恢复至上一稳定可用版本
4. **建立错误复盘闭环**
   每次AI引发错误后，记录错误原因、优化对应Prompt、补充约束规则，避免重复踩坑

### 4.4 标准化落地执行流程
1. 错误定级：发现AI代码问题，先判定错误等级
2. 快速止损：轻微问题直接修正；中重度问题立即暂停合并，回滚至稳定版本
3. 根源纠正：精准定位问题缺陷，针对性优化AI提示词、补充AGENTS.md约束
4. 重新验证：AI重新生成修正代码，完整走全流程验证环节
5. 复盘归档：记录问题与优化方案，沉淀经验，形成长效规避机制
